# Pinned to exact versions (2026-10-12 audit finding #11): `>=` meant every one
# of the ~96 ticks/day resolved and installed whatever the latest release was,
# inside a CI job that has `contents: write` -- a bad or compromised upstream
# release would run with push access to main.
#
# This file is the human-edited source. CI actually installs from
# requirements.lock (--require-hashes), which also pins every transitive
# dependency by hash. That lock is generated with `uv pip compile
# requirements.txt --universal --generate-hashes -o requirements.lock` --
# `--universal` is what makes this safe to generate on this Windows dev
# machine and still install correctly on CI's ubuntu-latest runner: it
# resolves and records hashes for every published platform's wheels (and the
# sdist) of each pinned version, not just the one this machine happens to
# download (a 2026-10-12 fix-check review correctly caught that an earlier
# version of this comment claimed a plain `pip-compile --generate-hashes`
# couldn't do this across platforms -- `--universal` is exactly the feature
# that makes it possible). Verified: a clean venv installed requirements.lock
# with `pip install --require-hashes` and ccxt's fetch_ohlcv worked against
# live Kraken data from it.
#

# this file changes. Bump deliberately (e.g. monthly), not passively.
