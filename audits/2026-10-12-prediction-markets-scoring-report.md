# Prediction markets (Polymarket) scoring: exploration only, 2 strategies survive correction -- not yet confirmed

- **Date:** 2026-10-12
- **Request:** continuation of the strategy-search program, the 3rd and last of the 7 live track families (crypto and stocks already tested -- see `audits/2026-10-12-full-strategy-search-audit-dossier.md`, `audits/2026-10-12-sol-xrp-ada-1h-scoring-report.md`, `audits/2026-10-12-stocks-scoring-report.md`).
- **Code:** `research_prediction_markets_scoring.py` (new, standalone, not committed) and `_local_dns_workaround.py` (new, local-machine-only, documented below). Invents **zero new strategies** -- reuses `research_harness.ALL_STRATEGIES` exactly as frozen in `PREREGISTRATION.md`.
- **Headline, stated up front: this is an exploration result, not a confirmed one.** Two strategies (`mean_reversion`, `bollinger_mean_reversion`) survive the pass gate and a formal Benjamini-Hochberg correction across the 6 strategies tested. This is the first time anywhere in this project's 126+ cells of prior testing that a result has survived formal correction. **It has not been held-out confirmed, the methodology that produced it is brand new and unreviewed, and every single "exploration pass" in this project's entire history so far (2 in the pre-registration round, 1 in round 4) has failed to survive a fresh out-of-sample test.** Treat this the same way: a lead, not a finding.

## Why this domain needed a different design, and a local-network workaround

The live `prediction_markets_momentum` track's own data source (`engine/data/prediction_source.py`) documents that Polymarket's Gamma API "only exposes the current price, not a rolling history" -- the live system builds history by polling and persisting prices itself. After the recent full reset, that reconstructed history was only ~1 week (668 ticks) -- confirmed too little for a meaningful test in `audits/2026-10-12-sol-xrp-ada-1h-scoring-report.md`'s discussion. Given a choice between stopping here or fetching real history from Polymarket's CLOB API, the request was to fetch real history.

**Local DNS issue, found and worked around:** `gamma-api.polymarket.com` and `clob.polymarket.com` fail to resolve via this machine's default DNS resolver (NXDOMAIN) but resolve correctly via public resolvers (8.8.8.8, 1.1.1.1) -- confirmed directly. This explains why this project's architecture runs all live ticks via GitHub Actions rather than locally (a different network, unaffected). `_local_dns_workaround.py` patches only the DNS lookup step (`socket.getaddrinfo`) for these two hostnames to known-good IPs from a trusted public resolver; **TLS certificate validation is untouched** (SNI/cert checks still happen against the real hostname), so this does not weaken security, it substitutes a working DNS answer for a locally broken one. Not imported by any live engine code.

**CLOB's `prices-history` endpoint only works for currently-active markets.** Confirmed directly: several high-volume historical markets (2020-2021 elections, 2024-2025 NBA Finals futures) all returned `{"history": []}` once closed, while active markets return real tick data. This means prediction-market "episodes" here are each market's available history up to now, not a complete resolved lifecycle -- a structurally different design than crypto/stocks' single continuous multi-year series.

## Method

1. **Market selection (2 passes, the first one failed and was corrected):**
   - First attempt sorted candidate active markets by raw 24h dollar volume. This surfaced a cluster of "will [longshot 2028 candidate] win the nomination" markets -- real recorded volume, but probabilities parked near-flat for a month. **Result: 0 trades generated by any of the 6 strategies on any of 20 such markets.** Caught immediately by the all-zero round-trip counts, not trusted.
   - Corrected: candidates are now pulled via the Gamma API's `order=volume24hr&ascending=false` parameter (confirmed this surfaces real, currently-live sports games and short-horizon markets -- NFL spreads, MLB games, European football -- which the unsorted/volume-sorted-wrong first attempt had missed entirely), paginated to 150 candidates, each candidate's full available CLOB history fetched, then the **20 most volatile** of the 145 candidates with >=100 ticks were kept as the final episode set. **Volatility, not raw volume, is the selection criterion** -- confirmed necessary, since volume and price movement are not the same thing for this asset class.
2. **Strategy test:** each of the 6 frozen strategies run independently on each of the 20 episodes via `run_cell` (episodes are different topics/timeframes, not concatenated).
3. **Combining across episodes:** per strategy, the per-episode p-values (excluding episodes with fewer than 2 closed round trips, where the harness's own `random_timing_pvalue` returns `None` by design) are combined into one p-value via **Fisher's method** -- the same method already used in this project to combine the SOL/XRP/ADA held-out p-values. Episodes here are mostly unrelated real-world events (a basketball game, a ceasefire question, a crude-oil threshold), so independence is on firmer ground than it was for SOL/XRP/ADA, **with one disclosed exception** (see Limitations).
4. **Pass gate, decided before running:** Fisher-combined p < 0.10 AND the strategy's total summed round-trip return, pooled across all episodes (realized trades only -- unrealized mark-to-market on any position still open at an episode's cutoff is excluded from this figure, since `summed_rt_return_pct` only sums closed round trips), is positive.
5. **Correction across strategies:** Benjamini-Hochberg at q=0.10 across the 6 strategies' combined p-values.

## Why this might be structurally real, and why it might not be

**A plausible mechanism exists that's specific to this asset class.** Unlike a crypto or stock price, a prediction-market probability is bounded in [0, 1] and news-driven: an event rumor can spike a probability sharply, after which it commonly partially unwinds as the news is digested or proven overstated, before the market eventually settles near its true resolution. This "overshoot and partial reversion" pattern is a more plausible structural feature of this asset class than it ever was for BTC/ETH/SPY, where mean-reversion ideas were tested repeatedly (CCI, Bollinger, linear regression channel, percentile rank, Connors RSI, Fisher Transform, return-shock reversion -- 7 separate mean-reversion-family ideas, 0 passes) and never once showed a real edge.

**But every reason for caution that has applied to every prior "pass" in this project applies here too, plus several new ones specific to this round's methodology:**

1. **This is exploration, not confirmation.** The 20 episodes were selected by realized volatility computed from the exact same data being tested -- the same category of selection that produced every exploration pass this project has ever found, none of which survived a subsequent held-out test. No held-out confirmation on a fresh, later-fetched set of markets has been run yet.
2. **Brand-new, unreviewed code.** `research_prediction_markets_scoring.py`, `_local_dns_workaround.py`, and the Fisher's-method combination function were all written in this session and have not been through the kind of independent review that caught real bugs in `research_harness.py` and `research_round4.py`'s Keltner plumbing. The Fisher combination math was spot-checked by hand (confirmed the closed-form chi-square survival function is correctly implemented) and a robustness check removing one disclosed non-independence issue (below) didn't change the conclusion -- but that is a long way from an independent audit.
3. **Two episodes are not independent of each other.** "Will the price of Bitcoin be above $82,000 on October 13?" and "...above $80,000 on October 13?" are both derived from the same underlying BTC price path over the same window -- a direct violation of Fisher's method's independence assumption. Checked directly: removing the duplicate from `mean_reversion`'s combination moves its p-value from 0.0011 to 0.0007-0.0016 depending on which is dropped -- **not a large effect**, so this specific violation doesn't appear to be driving the result, but it is a real flaw in the design that a more careful version should avoid (e.g., by excluding near-duplicate markets on the same underlying event before combining).
4. **Several episodes contributed only 2-4 closed round trips each.** The random-timing p-value test was built and validated against thousands-of-round-trip crypto/stock series; its behavior with this few round trips per episode, where the pool of valid random start points is itself constrained by a short series, is unvalidated territory.
5. **`fee_pct=2.0, slippage_pct=0.5`** (the live `prediction_markets_momentum` track's own assumptions) were applied uniformly, same as every other round in this project -- not tuned for this result.
6. **No engine code, live ledger, or config was touched.** This is a pure research artifact.

## What would be needed before trusting this

Per the same discipline this project has applied to every prior pass (most recently Keltner's separate pre-registration in `PREREGISTRATION-keltner.md`): **freeze the exact strategy (`mean_reversion` and/or `bollinger_mean_reversion`, exact existing parameters, no retuning), freeze the exact episode-selection method, and score it once on a genuinely fresh set of markets fetched at a later date** -- not re-selected from the same snapshot used here. Given prediction markets churn much faster than crypto/stocks (most episodes here span days to a few weeks), a meaningful held-out test could plausibly happen on a much shorter horizon than the 2027 crypto/Keltner scoring windows -- worth a deliberate decision rather than an automatic extension of those dates.
